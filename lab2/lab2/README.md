# Лабораторная работа 2 — Docker

Сервис из лабы 1 упакован в три контейнера: `frontend` (nginx — статика + прокси
`/api`), `backend` (Flask API через gunicorn) и `db` (PostgreSQL). Nginx —
упрощённая версия конфига лабы 1: статика + проксирование `/api` + кастомные
`404.html`/`50x.html`. TLS, виртуальные хосты, `/admin` и rate-limit уже были
продемонстрированы в лабе 1 на голом хосте и здесь не дублируются (скажи, если
хочешь, чтобы они тоже были внутри контейнера — добавить несложно).

## Запуск (PowerShell, Docker Desktop должен быть запущен)

```powershell
cd lab2
Copy-Item .env.example .env
# ОБЯЗАТЕЛЬНО поменяйте DB_PASSWORD в .env — приложение само откажется
# стартовать с паролем "CHANGE_ME" (это защита из app.py, не моя добавка)
docker compose up -d --build
```

Открыть http://127.0.0.1:8080 — должна работать та же форма с заметками,
что и в лабе 0, только через nginx и отдельный backend-контейнер.

## Проверки

Скрипт `check.sh` рассчитан на Git Bash / WSL (как и check-скрипт из лабы 1).
Запуск:

```bash
cd lab2
bash check.sh
```

Он по очереди:
1. собирает `lab2-backend:bad` и `lab2-backend:good`;
2. сравнивает размер образов (`docker images`);
3. показывает `whoami` внутри хорошего образа — не root;
4. меряет время пересборки после правки одной строки `app.py` для обоих
   образов (`time docker build …`) — у хорошего пересборка быстрее, потому
   что слой с `pip install` не инвалидируется;
5. поднимает стек и показывает `docker compose ps`;
6. пишет заметку через API, удаляет контейнер `db` (`docker compose rm -sf db`),
   поднимает его заново — заметка остаётся (данные в именованном томе `db_data`);
7. проверяет сетевую изоляцию — из контейнера `frontend` запрос к `db:5432`
   падает (frontend не подключён к `backend-net`).

Если нужно вручную — `docker exec <контейнер_backend> whoami` и
`docker rm` по отдельности делают то же самое, что шаги 3 и 6 скрипта.

## Bad vs good — что в отчёт

| # | Плохая практика (`Dockerfile.bad`)                          | Как исправлено (`Dockerfile.good`)                                   |
|---|--------------------------------------------------------------|------------------------------------------------------------------------|
| 1 | `FROM python:latest` — непредсказуемая, невоспроизводимая сборка | `FROM python:3.13.0-slim` — зафиксированная версия и минимальный базовый образ |
| 2 | `ENV DB_PASSWORD=...` — секрет зашит в слой образа            | Пароль приходит из окружения `docker compose` / CI-секретов, в образе его нет |
| 3 | `COPY . .` → `RUN pip install` — ломает кеш слоёв при правке кода, тащит мусор без `.dockerignore` | `requirements.txt` копируется и ставится отдельным слоем до кода; есть `.dockerignore` |
| 4 | Нет `USER` — процесс работает от root                        | Отдельный непривилегированный `appuser`                               |
| 5 | Нет `HEALTHCHECK`                                             | `HEALTHCHECK` на `/api/health` (эндпоинт приложения, заодно проверяет БД) |
| 6 | Один слой, build-инструменты и pip-кеш остаются в финальном образе | Multi-stage build: зависимости ставятся в `builder`, в финальный образ копируется только `/usr/local` |
| 7 | Запущен dev-сервер `flask run` (однопоточный, не для продакшена)  | Запущен `gunicorn` с несколькими воркерами (он уже в `requirements.txt`) |

В отчёт по этому пункту: оба Dockerfile, таблица выше (или свой пересказ),
вывод `docker images` с размерами, вывод `time docker build` для обоих
образов с объяснением разницы, `whoami` внутри хорошего образа.

## Что заскриншотить для остальной части отчёта

- `docker compose up -d --build` и `docker compose ps` — все три сервиса `healthy`/`running`.
- Форму на http://127.0.0.1:8080 с сохранённой записью + ту же запись в таблице
  `notes` (как в лабе 0, но теперь через `docker compose exec db psql …`).
- Персистентность: запись → `docker compose rm -sf db` → `docker compose up -d db`
  → запись осталась.
- Сетевая изоляция: `docker compose exec frontend wget -T 3 -O- http://db:5432` падает с ошибкой.
